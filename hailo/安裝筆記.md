# Hailo 工具安裝筆記（DFC 5.4.0、HailoRT 5.4.0）

> 2026/11/04 讀 Hailo Developer Zone 的官方文件（v5.4.0，要登入才看得到）整理的重點，用我們自己的話寫。
> 指令、錯誤訊息、實測數字照舊寫進 [`結果.md`](結果.md)；計畫在 [`轉換計畫.md`](轉換計畫.md)。

## 兩個工具各做什麼

| | 做什麼 | 在哪裡跑 | 安裝檔 |
| --- | --- | --- | --- |
| **Dataflow Compiler（DFC）** | ONNX → HEF（parse → optimize 量化 → compile），附模擬器 | 只有 Linux；Windows 要透過 WSL2（WSL 裡也能用 NVIDIA GPU，要多一個設定，見下面） | `hailo_dataflow_compiler-5.4.0-py3-none-linux_x86_64.whl`（通用 Python 3.10–3.12） |

## USB 供電會影響速度（量 FPS 前一定要看）

官方文件直接點名 ASUS UGen300：要接在能供 **3.0 A** 的 USB-C 埠才是全速。主機宣告的電流比較低時，晶片會自動降頻：

| 主機宣告的電流 | 效能 |
| --- | --- |
| 3.0 A | 全速 |
| 1.5 A | 最多慢 25% |
| 0.9 A，或用轉接頭接 USB Type-A 埠 | 最多慢 50% |

- 所以 benchmark 結果要記下接在哪個埠、用什麼線；同一顆 HEF 換個埠，數字可能差一半。
- 筆電的 USB-C 埠能不能供 3.0 A，官方規格沒查到；USB-C 電流計可以看實際電流。
- 筆電的 CPU 是 Intel Tiger Lake 世代，文件說這一代的 USB 控制器在**重開機後可能認不到裝置**，解法是拔掉再插。

## DFC 安裝（WSL2 裡的 Ubuntu）

1. 裝 Ubuntu（PowerShell，要按確認）：`wsl --install -d Ubuntu-24.04`。選 24.04 是因為它內建 Python 3.12，跟專案一樣。
2. 系統套件：`sudo apt-get update && sudo apt-get install python3.12-dev python3-tk graphviz libgraphviz-dev pkg-config python3-virtualenv`
3. 建虛擬環境、裝 DFC（放在 WSL 自己的家目錄，比放在 `/mnt/c` 快）。**Python 3.12 要先自己編 onnxsim**，原因見 [`結果.md`](結果.md)「DFC 安裝」：
   ```
   virtualenv -p python3.12 ~/hailo_dfc && . ~/hailo_dfc/bin/activate
   pip install setuptools wheel "cmake<4"
   CMAKE_BUILD_PARALLEL_LEVEL=12 pip install --no-build-isolation onnxsim==0.4.36
   pip install ~/hailo_sdk/hailo_dataflow_compiler-5.4.0-py3-none-linux_x86_64.whl
   ```
   需要網路（會下載 TensorFlow 和 NVIDIA 的 CUDA 函式庫，虛擬環境約 11 GB）。
4. 確認：`hailo --version`（應該是 v5.4.0）、`pip freeze | grep hailo`。第一次執行會檢查系統需求；在 WSL 裡會警告找不到 CUDA／cuDNN（系統層級的），但 DFC 自己帶的 TensorFlow 和 CUDA 函式庫還是抓得到 GPU。
5. **在路徑沒有空白的資料夾執行 `hailo`**（例如 `~/work`）：DFC 會把 log 寫在目前的資料夾，路徑裡有空白時寫不進去。repo 在 WSL 裡的路徑是 `/mnt/c/Users/user/ASUS hackathon`，有空白，所以 ONNX 和校正圖要用完整路徑指過去，指令在 `~/work` 下執行。
6. **讓 GPU 能用**：WSL 裡 TensorFlow 抓得到筆電的 GPU，但量化時會出現 `libdevice not found at ./libdevice.10.bc` → `JIT compilation failed. [Op:Log]`。檔案其實在 triton 套件裡，照 XLA 要的資料夾結構接過去，再把兩個環境變數加進虛擬環境的 activate：
   ```
   mkdir -p ~/hailo_dfc/cuda_data/nvvm/libdevice
   ln -sf ~/hailo_dfc/lib/python3.12/site-packages/triton/backends/nvidia/lib/libdevice.10.bc ~/hailo_dfc/cuda_data/nvvm/libdevice/
   echo >> ~/hailo_dfc/bin/activate   # DFC 的 activate 最後一行沒有換行，先補一個，不然下一行會接在它後面
   echo 'export XLA_FLAGS=--xla_gpu_cuda_data_dir=$HOME/hailo_dfc/cuda_data' >> ~/hailo_dfc/bin/activate
   echo 'export TF_FORCE_GPU_ALLOW_GROWTH=true' >> ~/hailo_dfc/bin/activate
   ```
   不想用 GPU 時，執行前設 `CUDA_VISIBLE_DEVICES=`。

## 轉換流程

- 主要 API 是 `ClientRunner`，三個階段，每個階段都能存成 `.har`、之後再讀回來：
  1. **parse**（`translate_onnx_model()`，CLI 是 `hailo parser onnx`）：用 `end_node_names` 把後處理切掉，RTMO 要切在解碼之前。
  2. **optimize**（`optimize()`，CLI 是 `hailo optimize`）：量化，要給校正圖。進階設定寫在 model script（`.alls`），用 `load_model_script()` 載入。
  3. **compile**（CLI 是 `hailo compiler`）：輸出 HEF。
- **模擬器**有三種：parse 後的 `SDK_NATIVE`（浮點）、`SDK_FP_OPTIMIZED`（加了正規化等修改、還沒量化）、optimize 後的 `SDK_QUANTIZED`（量化後）。我們比對的是 `SDK_QUANTIZED` 對 ONNX。
- 量化後準確度掉太多：用 `analyze_noise()`（CLI 是 `hailo analyze-noise`）找出是哪一層。
- model script 常用指令：`normalization`（晶片上做正規化）、`resize`、`input_conversion`（色彩轉換）、`model_optimization_flavor(optimization_level=…, compression_level=…)`、`quantization_param(<層>, precision_mode=a16_w16)`（敏感的層改 16 位元）、`set_seed`（讓量化結果可重現）。

## 量化等級和校正張數（重要）

DFC 5.4.0 原始碼裡的說明（`hailo_model_optimization/acceleras/model_optimization_config/mo_config.py`，2026/11/05 讀的；文件寫「每版可能會變」）：

| `optimization_level` | 做什麼 |
| --- | --- |
| 0 | Equalization（調整相鄰層的數值範圍，讓量化誤差小一點） |
| 1 | 0＋反覆的偏差校正（bias correction） |
| 2 | 0＋微調（finetune）4 個 epoch、1024 張 |
| 3 | 0＋Adaround 320 個 epoch、256 張、所有層 |
| 4 | 0＋Adaround 320 個 epoch、1024 張、所有層 |

- **不指定時依硬體決定**：只有 CPU 是 0；有 GPU、校正圖少於 1024 張是 1；有 GPU、至少 1024 張是 2。所以 `hailo/compile_hef.py` 明確寫死等級，不讓結果跟著電腦變。
- **校正預設只用 64 張**（`model_optimization_config(calibration, calibset_size=…)` 預設 64）：給再多張也只拿前 64 張算各層範圍，要用更多張得在 model script 裡寫明。
- 偏差校正和微調都用校正圖讓量化後的輸出貼近 **ONNX 自己的輸出**，不看標註。
- **偏差校正會寫很大的暫存檔**：在目前的資料夾建 `bias_correction_cache_*`，YuNet、768 張約 13 GB（log 說「最多 15 GB」）。11/05 就是這個把 C 槽寫滿的。
- 4 位元壓縮（`compression_level`，預設 1）只對參數超過 2000 萬的模型生效（`MINIMUM_PARAMS_FOR_COMPRESSION`），YuNet 不會被壓縮。
- 官方的參考時間（ResNet-v1-50、A4000 GPU）：等級 0 約 1 分鐘、等級 2 約 4 分鐘、等級 3 約 47 分鐘、等級 4 約 3 小時。筆電 RTX 3050 上，YuNet 收集 768 張的統計約 44 秒。
- 對我們的影響：YuNet 用等級 0 就夠的話最簡單。RTMO 量化後掉太多時，依序試：把敏感的層改 16 位元、等級 1（先騰出磁碟空間）、等級 2（要 1024 張校正圖，4 GB 顯示記憶體可能不夠）。

## C 槽空間

- WSL 的 Ubuntu 整個裝在 C 槽的一個虛擬磁碟檔案裡（`%LOCALAPPDATA%\wsl\{…}\ext4.vhdx`）。WSL 裡 `df` 看到的 1 TB 是虛擬磁碟的上限，**不是 C 槽實際剩下的空間**；要看 C 槽剩多少，在 WSL 裡用 `df -h /mnt/c`。
- 虛擬磁碟用多少長多少，**檔案刪掉後不會自己縮回去**。要把空間還給 Windows（三個地方，看提示字元分）：
  1. Ubuntu 的視窗（`userharry@…:~$`）：`sudo fstrim -av`（問的是 Ubuntu 的密碼），然後 `exit`。
  2. 系統管理員身分的 PowerShell（`PS C:\WINDOWS\system32>`）：`wsl --shutdown`，然後 `diskpart`。
  3. diskpart（`DISKPART>`）裡依序輸入（虛擬磁碟的位置用
     `(Get-ChildItem HKCU:\Software\Microsoft\Windows\CurrentVersion\Lxss | Get-ItemProperty | ? DistributionName -eq Ubuntu-24.04).BasePath` 查）：
     ```
     select vdisk file="<上面查到的資料夾>\ext4.vhdx"
     attach vdisk readonly
     compact vdisk
     detach vdisk
     exit
     ```
  - 壓縮時 WSL 不能開著（開了會鎖住虛擬磁碟）；diskpart 的指令打在 Ubuntu 裡會出現 `syntax error near unexpected token`。
  - 11/05 壓縮一次：虛擬磁碟 31.3 GB → 13.9 GB，C 槽剩 17.1 GB → 34.7 GB。
- C 槽滿的時候，執行中的 DFC 會當掉（`Bus error`），WSL 也會讀寫錯誤（`getpwnam(userharry) failed 5`），騰出空間後 `wsl --shutdown` 再開就恢復。

## 在國網中心 nano4 跑 DFC（H200，2026/11/05）

筆電的 RTX 3050 只有 4 GB，RTMO 的量化微調放不下（batch 2 就 `GPU memory has been exhausted`），所以搬到國網中心的 nano4。

- 環境：登入節點 RHEL 9.6、系統 Python 3.9（DFC 要 3.10–3.12）、沒有 root；GPU 節點每台 8 張 H200、112 顆 CPU、1.9 TB 記憶體，用 Slurm 排程。`dev` partition 一個工作最多 4 小時、每人同時跑 2 個（其他的排隊，原因寫 `QOSMaxJobsPerUserLimit`）。
- 登入要密碼＋2FA（手機 OTP、推播或 email）。從筆電用 WSL 的 ssh 開一條主連線，之後的 ssh／rsync 都走它，不用每次驗證：
  ```
  wsl -d Ubuntu-24.04 -- ssh -NM -o ControlPath=/home/<WSL 使用者>/.ssh/cm-nano4 -o ServerAliveInterval=60 -o ServerAliveCountMax=5 <帳號>@nano4.nchc.org.tw
  ```
  在前景跑、視窗保持開著；用 `-f` 丟到背景的兩次都撐不久，而且斷了看不到原因。其他指令走這條連線：`ssh -n -o ControlPath=… <帳號>@nano4.nchc.org.tw '…'`、`rsync -e "ssh -o ControlPath=…"`。
  - **ssh 要加 `-n`**：用 `bash -s < 腳本` 執行時，沒加 `-n` 的 ssh 會把後面的腳本當成自己的輸入吃掉，後面幾行都不會執行（而且不會報錯）。
- 安裝（在登入節點跑，約 30 分鐘，裝好 11 GB）：
  ```
  module load miniconda3/26.1.1 && eval "$(conda shell.bash hook)"
  conda create -y -p ~/hailo_dfc -c conda-forge --override-channels python=3.12 pygraphviz graphviz
  conda activate ~/hailo_dfc
  pip install setuptools wheel "cmake<4"
  CMAKE_BUILD_PARALLEL_LEVEL=8 pip install --no-build-isolation onnxsim==0.4.36
  pip install hailo_dataflow_compiler-5.4.0-py3-none-linux_x86_64.whl
  ```
  沒有 root 不能 apt，graphviz 從 conda-forge 裝；只用 conda-forge 的 channel，不用接受 Anaconda 預設 channel 的條款。裝完照上面第 6 步接 libdevice（路徑換成 `~/hailo_dfc/lib/python3.12/site-packages/triton/…`）。
- 卡住過的：DFC 寫死 `matplotlib==3.5.2`，它沒有 Python 3.12 的預編譯檔，要從原始碼編；編譯時要從 `http://www.qhull.org` 下載 qhull，nano4 連不到（`Failed to download any of the following: ['http://www.qhull.org/download/qhull-2020-src-8.0.2.tgz']`）。解法：在別台電腦下載 `qhull-2020-src-8.0.2.tgz`，放到 nano4 的 `~/.cache/matplotlib/b5c2d7eb833278881b952c8a52d20179eab87766b00b865000469a45c1838b7e`（檔名就是 sha256；matplotlib 編譯時會先找這個快取）。筆電的 WSL 連得到 qhull.org，所以當初沒遇到。
- 登入節點的 GPU 一般程式用不了（`Unable to determine the device handle for GPU0`，DFC 會退回 CPU）；量化要用 Slurm 送到 GPU 節點，例如 `sbatch -A <計畫代號> -p dev --gres=gpu:1 --cpus-per-task=12 --mem=200G -t 04:00:00 …`。工作裡要先 `module load miniconda3/26.1.1`、`conda activate ~/hailo_dfc`、設 `XLA_FLAGS`。
- sbatch 的 `--export=VAR=值` 用逗號分隔變數，值裡有逗號（例如 model script 的參數）會被切開：改成先設環境變數、再用 `--export=ALL`。
- `dev` partition 每張 GPU 最多配 12 顆 CPU（`--cpus-per-task=16` 會被拒：`CPU per node specification of 16 exceeds the limit (1 * 12)`）。
- 偶爾分到 GPU 有問題的節點：`cudaSetDevice() on GPU:0 failed. Status: CUDA-capable device(s) is/are busy or unavailable`。重送時用 `--exclude=<節點>` 避開。
- **編 HEF（compile）在 nano4 會失敗**（2026/11/06）：`hailo_tools/build/compiler: /lib64/libstdc++.so.6: version 'GLIBCXX_3.4.30' not found` → `BackendInvalidInputArgsException: Compilation failed with unexpected crash`。系統的 libstdc++ 是 6.0.29（太舊），conda 環境裡的是 6.0.36。解法：`conda activate` 之後 `export LD_LIBRARY_PATH="$CONDA_PREFIX/lib:$LD_LIBRARY_PATH"`。筆電的 Ubuntu 24.04 沒有這個問題。

## HailoRT 安裝（Windows，2026/11/06 實際裝過）

**先知道 UGen300 怎麼開機**：每次插上，裝置先進 **loader 模式**（裝置管理員的匯流排名稱是 `UGen300 USB Loader`）。HailoRT 的背景服務 `hailo_usb_service`（LocalSystem，自動啟動）收到「插入」事件後，會執行 `hailo_usb_loader rfs-upload`，把系統映像（`C:\Windows\System32\drivers\hailo\hailo10h_usb\core-image-hailo-hailo10-usb-dongle.ext4`，約 100 MB）傳進裝置。大約 10 秒後，裝置變成 `UGen300 USB AI Accelerator (Hailo-10H)`，這時才能跑模型。

1. 執行 `HailoRT_5.4.0_windows_installer.msi`。功能選單裡：
   - **Python Package (pyHailoRT)** 選「Entire feature will be installed on local hard drive」。
   - **USB 驅動那一項要勾**，PCIe 不用。安裝程式規定至少要勾一個驅動。之後用「變更」模式補裝時，已經裝過的項目如果變成 ✕，會被移除。
2. 裝完**把 UGen300 拔掉再插**（接在能供 3.0 A 的 USB-C 埠）。安裝前就插著的話，服務沒看到插入事件，裝置會一直停在 loader 模式。
3. `hailortcli scan` 找得到裝置，`hailortcli fw-control identify` 要印出 `Firmware Version: 5.4.0 (release,app)`、`Device Architecture: HAILO10H`。
4. 開始選單的「Hailo USB FW Update」（`usb_fw_update.exe`，會要求系統管理員權限）要顯示「Firmware is up to date」。它用 `…\hailo10h_usb\version` 這個檔案判斷版本（11/06 寫進去的是 `1.11.11`）。
5. pyHailoRT 的 wheel 在 `C:\Program Files\HailoRT\python`，有 cp310～cp313。專案環境是 Python 3.12，先把 `hailort-5.4.0-cp312-cp312-win_amd64.whl` 複製出來，再執行 `uv pip install --python .venv <wheel 路徑>`。它只依賴 numpy。
   - 它不在 `pyproject.toml` 裡（wheel 只在 HailoRT 安裝檔裡，不能放進公開的 repo）。`uv run` 不會移除它，但 **`uv sync` 會**，sync 之後要重裝。
- USB 驅動包在安裝檔裡（Windows 內建的 WinUSB），不用另外裝。
- 重開機或拔插之後，如果 `identify` 又說韌體不相容，先看裝置管理員的匯流排名稱：還是 `UGen300 USB Loader` 的話，拔掉再插。

**11/06 卡住的經過**（照上面的順序做就不會碰到）：

| 看到的 | 原因 | 解法 |
| --- | --- | --- |
| `hailortcli fw-control identify` → `Hailo USB device detected, but its firmware version is incompatible. Please update the firmware by running: hailo_usb_loader fw-update`（`HAILO_INVALID_FIRMWARE(23)`） | 裝置停在 loader 模式，系統沒傳進去。安裝 HailoRT 前就插著，服務沒收到插入事件 | 拔掉再插 |
| 更新工具：`Scan failed – Timed out waiting for USB device to transition to functional mode.`，log（`%LOCALAPPDATA%\Hailo\fw_update.log`）寫 `unexpected device firmware version ''` | 同上；它等裝置變成可運作模式等不到。`''` 是因為 `version` 檔還不存在 | 同上 |
| `hailo_usb_loader fw-update`（命令列）跑 2 分鐘後 `Failed to open version file …\hailo10h_usb\version for writing` | 沒用系統管理員權限，寫不進 `System32\drivers` | 用開始選單的更新工具（會自己要求系統管理員權限） |

## Python 呼叫方式

```python
from hailo_platform import VDevice
with VDevice() as vdevice:
    infer_model = vdevice.create_infer_model("yunet.hef")
    with infer_model.configure() as configured:
        bindings = configured.create_bindings()
        bindings.input().set_buffer(frame)          # 形狀照 infer_model.input().shape
        bindings.output(name).set_buffer(out_buf)   # YuNet 有 12 個輸出，用名字分
        configured.run([bindings], timeout_ms)       # 也有 run_async
```

- RTMO 和 YuNet 要放在同一顆晶片上一起跑：在同一個 `VDevice` 上各開一個 `create_infer_model`，HailoRT 的排程器會輪流執行。跨程序共用才需要 `group_id = "SHARED"` 和 multi-process service。
- 輸入、輸出可以設成 `FLOAT32`，HailoRT 會自己做量化和反量化；也可以用 `uint8` 省掉轉換。
- 實際包好的版本在 [`hailo_infer.py`](hailo_infer.py)（輸出設成 float32、非同步送一批）。兩個要注意的地方：
  - **輸入陣列要可寫**：`np.load(..., mmap_mode="r")` 讀出來的會報 `ValueError: array is not writeable`。
  - **`configure()` 回傳的物件要先 `shutdown()`，再釋放 `VDevice`**：順序反了，會印 `Lost communication with the server`。

## 量測工具（11/06 在 UGen300 上確認過）

| 指令 | 用途 |
| --- | --- |
| `hailortcli parse-hef x.hef` | 看輸入／輸出格式、context 數 |
| `hailortcli benchmark x.hef` | 這台只印 FPS 和溫度 |
| `hailortcli run2 -t 10 --measure-latency --measure-overall-latency --measure-temp set-net x.hef --batch-size 1` | 晶片延遲、含主機的延遲、溫度（量延遲時一次送一張，不算 FPS） |
| `hailortcli run2 -t 10 -j out.json set-net x.hef --batch-size 8` | FPS；多個 `set-net` 就是多個模型同時跑 |

- `hailortcli run` 不支援這台（`The "run" command is not supported for this device type! Use "run2" instead.`）。
- `run2 -m raw_async`／`raw_sync` 也不支援（`HAILO_NOT_IMPLEMENTED(7)`，Hailo-10 要用 InferModel）；用預設的 `full_async`。
- **功耗、電流都量不到**（`Measurement power is not supported`）。**要買 USB-C 電流計**。
- `hailortcli` 會在目前的資料夾寫 `hailort.log`，沒有寫入權限的資料夾（例如 `C:\Program Files\HailoRT\bin`）會警告；在 `%LOCALAPPDATA%\Hailo` 之類的地方執行。
